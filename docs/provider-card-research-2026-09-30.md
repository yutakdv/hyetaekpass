# 카드 혜택·개인 실적·결제 코드 연동 1차 조사

확인일: **2026-09-30 (Asia/Seoul)**. 공식 공개 페이지와 개발 규격의 읽기 조사다. 계정 생성·이용 신청·고객 인증·실카드 API 호출·제휴·사용권 확인은 수행하지 않았다. 상품 혜택 금액·카드 이미지·상품 원문을 운영 카탈로그에 복사하지 않았다.

## 핵심 판정

**카드 상품의 공개 조건을 읽는 일, 고객이 가진 카드·거래를 조회하는 일, 결제용 QR을 발급하는 일은 서로 다른 연동이다.** 공식 상품 안내는 존재하고 개인 카드 조회 API도 존재한다. 이를 무료·무인증 API 하나로 연결하여 모든 카드의 지금 쓸 혜택과 결제 QR을 가져올 수 있다고 확인한 것은 아니다.

| 필요한 데이터 | 이번에 확인한 경로 | 현재 혜택패스의 가능 범위 |
|---|---|---|
| 카드 상품의 일반 혜택·제외·실적 기준 | 각 카드사 공식 상품 페이지·상품설명서 | 공식 링크 안내. 자동 계산용 변환·배포는 이용권과 실제 원문 검수 이후 |
| 고객의 카드 목록·기본·청구 정보 | 금융결제원 오픈뱅킹 카드 API | 테스트베드 탐색과 운영 이용 자격·계약 확인을 별도로 진행해야 함 |
| 고객의 승인·매입·포인트 등 | 금융 마이데이터 카드 업권 정보제공 API | 해당 사업자 자격·인증·전송요구·동의·보안 절차를 갖춘 연동이 필요 |
| 상품별 실적 충족·이번 달 남은 할인 한도 | 카드사 개인 서비스 또는 제휴 데이터 후보 | 검토한 공통 규격에서 전용 항목을 확인하지 못함. 거래액 합계로 임의 확정 금지 |
| 카드 결제 QR·바코드 | 발급사/참여기관의 결제 앱과 결제 체계 | 현재 앱의 정적 멤버십 코드 저장과 별개. 일반 QR 생성기로 대체할 수 없음 |

## 1. 금융결제원 오픈뱅킹

공식 개발자사이트의 API 목록에 **카드목록조회, 카드기본정보조회, 카드청구기본정보조회, 카드청구상세정보조회**가 있다. 따라서 “오픈뱅킹은 은행계좌만 조회한다”는 설명은 부정확하다. 해당 공개 목록에서 상품별 혜택 규칙·개인별 할인 잔여 한도·카드 결제 코드 발급 API는 확인하지 못했다. [금융결제원 오픈API 개발자사이트](https://developers.kftc.or.kr/dev)

개발자사이트는 개발·시험 이후 별도의 이용 신청으로 사업화를 진행하도록 안내하고, 서비스 성격에 따른 추가 서류와 심사·승낙/거절 절차를 약관에 둔다. 테스트 계정 생성이나 API 목록 열람을 실제 고객 카드 정보의 운영 조회 승인으로 해석하면 안 된다. 실제 업무의 이용기관 요건·지원 카드사·데이터 범위·비용·보안 점검·계약은 [금융결제원 통합포털](https://openapi.kftc.or.kr/)과 운영 신청 과정에서 확인할 사항이다. [개발자사이트 회원가입·이용약관](https://developers.kftc.or.kr/dev/user/register)

확인 수준: 목록·개발자 약관을 읽었다. 카드 API의 운영 자격 취득, 전체 요청/응답 규격의 계약 확인, 실사용 토큰 발급·호출은 하지 않았다. 통합포털 본문은 이번 직접 열람에서 동적 콘텐츠가 추출되지 않아 운영 FAQ의 세부 요건은 확정하지 않았다.

## 2. 금융 마이데이터

공식 테스트베드의 카드 업권 정보제공 규격은 API 요청자를 **마이데이터사업자**로 표시한다. 확인한 페이지의 카드 목록·기본정보·포인트·청구·국내외 승인·매입 API는 `v2`, 표시 개정일은 **2025-09-30**이다. 예를 들어 카드 기본정보는 `/v2/card/cards/{card_id}`, 포인트는 `/v2/card/points`다. 포인트는 고객 단위로 관리하며 카드별 할인 잔여 한도가 아니다. [카드 업권 정보제공 API 규격](https://developers.mydatakorea.org/mdtb/apg/mac/bas/FSAG0406?id=2)

검토한 규격의 목차·항목에서는 카드 상품의 할인 산식, 상품별 혜택 실적 충족 판정, 이번 달 잔여 할인 한도, 결제 QR 발급을 확인하지 못했다. 이는 해당 공개 규격의 확인 결과이며, 모든 카드사 비공개 제휴 API까지 부재함을 증명한 것은 아니다. 카드 목록의 상품명·기본정보의 발급일만으로 상품 Edition·개인 적용 약관·혜택 옵션까지 자동 확정할 수 있다는 근거도 확보하지 못했다. [동일 공식 규격](https://developers.mydatakorea.org/mdtb/apg/mac/bas/FSAG0406?id=2)

본인신용정보관리업의 영위에는 법 제4조의 허가가 적용된다. 혜택패스가 직접 이 업무를 영위하는 방식인지, 적법한 사업자와 제휴·위수탁하는 방식인지 먼저 정해야 한다. 제휴 계약만으로 모든 허가 의무가 사라진다고 단정하지 않는다. [신용정보의 이용 및 보호에 관한 법률 제4조](https://law.go.kr/LSW/lsLinkCommonInfo.do?lsJoLnkSeq=1020413625)

공식 중계기관 안내는 고객의 전송요구, 안전한 REST/JSON 교환, TLS 상호 인증, 계약 후 제공되는 테스트 가이드를 설명한다. 코스콤 안내는 금융투자·전자금융·대부 업권 전담 역할을 명시하므로, 이를 카드 업권의 계약 창구라고 자동 판단하지 않는다. 최신 운영 규격은 한국신용정보원 종합포털의 자료와 해당 업권 담당 체계에서 재확인해야 한다. [코스콤 금융 마이데이터 소개](https://www.k-mydata.org/finMydata/about), [공식 API FAQ](https://www.k-mydata.org/support/faq)

금융위원회는 2025년 6월 금융 마이데이터 2.0의 업권별 자산 조회·동의 절차·전송주기 등의 개선을 발표했다. 이 제도·서비스 명칭은 각 엔드포인트의 `v2`와 별개이며, 혜택패스의 계산 모델 버전도 아니다. 이번 조사로 혜택패스의 참가·허가·연동 완료가 확인된 것은 아니다. [금융위원회 마이데이터 2.0 서비스 개시 자료](https://www.fsc.go.kr/no010101/84780)

## 4. 카드 QR과 멤버십 코드의 구분

삼성 공식 앱카드 약관은 앱카드 결제 번호를 NFC·QR·바코드 형태의 **일회용 카드번호와 이미지**로 설명한다. 오프라인 사용도 결제 앱 실행·인증 후 생성된 번호를 제시하는 흐름이다. 공개된 상품명이나 고객 카드 식별자로 혜택패스가 같은 결제 코드를 생성할 수 있다는 근거가 없다. [삼성카드 앱카드 이용약관](https://www.samsungcard.com/personal/customer-service/conditions/appcard/UHPPCC0404M0.jsp)

KB Pay 공식 안내도 등록된 결제수단과 본인인증을 거친 바코드/QR·NFC 등 결제 흐름을 설명한다. 매장 제시 코드, 가맹점에서 고객이 스캔하는 QR, 온라인 PC 인증 QR, 앱 다운로드 QR은 목적이 달라 같은 데이터로 취급하면 안 된다. [KB Pay 이용 안내](https://card.kbcard.com/SVC/DVIEW/HSCMCXPRISVC0128)

제품 제안: 카드의 결과 화면은 사용할 카드 이름·조건·사용 순서를 안내하고, 공식 앱/안내 경로로 연결한다. 정적 멤버십 코드 등록 기능에 카드 결제 QR·카드번호·금융 인증값을 넣지 않는다. 결제 발급 체계의 공식 제휴·SDK/API·보안·약관·운영 승인과 양 OS 시험을 확보하기 전에는 카드 QR 가져오기/발급을 구현 완료로 표시하지 않는다.

## 5. 현재 계산 모델과 버전 근거

로컬 코드 확인 근거는 `contracts/types.ts`, `FE/mobile/src/service.ts`, `packages/benefit-core/package.json`이다. 그래프의 `productVersion` 탐색 결과가 부족해 이 알려진 파일의 실제 소스를 읽었다. 코드 수정은 하지 않았다.

- 카탈로그의 `schemaVersion: 1`·`semanticsVersion: 1`은 앱 계약 버전이다. 계산 패키지의 `0.1.0`은 배포 패키지 버전이다. 금융 마이데이터 엔드포인트 `v2`와 혼동하지 않는다.
- `WalletItem.productVersion: string | null`은 현재 사용자가 입력한 값이다. 공식 발급 상품·적용 약관·Edition을 API로 확인한 증거가 아니다. 자유 이름·버전 입력으로 지원 상품을 자동 연결하거나 자격을 충족 처리하지 않는다.
- `Catalog.products`에는 `id/name/kind`가 있고, 별도의 발급사별 약관 버전 매핑 계약은 현재 없다. `Source.documentVersion`과 `Rule.version`은 확보한 원문·검수 규칙의 변경 추적이다. 이름이 같은 구판·신판을 자동 일치시킬 근거로 확대하지 않는다.
- 현 모델은 명시된 정률/정액, 기준금액, 최소금액, 상한, 반올림, 즉시/청구 정산과 검수된 조합을 처리한다. 포인트·리터당/천원당 혜택·실적 구간·시간대·자동 선택 옵션 등은 원문 의미와 지원 산식을 확인해야 하며, 의미가 부족하면 메모/안내 전용 또는 UNKNOWN으로 남긴다.

승인된 데이터 연동을 추진할 때는 발급사 식별자 → 실제 상품 식별자/형태 → 적용 약관·옵션/효력 기간 → 검수된 규칙 버전의 명시적 매핑이 먼저 필요하다. API가 알려 주는 상품명과 거래 합계만으로 개인 실적 충족·잔여 한도를 계산했다는 표시를 하지 않는다. 취소·매입·실적 제외·월 경계·합산 카드·옵션 등 의미가 일치하는지 별도로 확인해야 한다.

## 6. 통합 순서 제안과 남은 외부 조건

1. **지금 가능한 제품 경로:** 카드사/상품 선택과 공식 조건·공식 앱 안내를 제공하고, 보유 정보와 확인한 조건은 단말에서 기록한다. 공개 계산 0개·실적 모름 상태도 그대로 사용 가능하게 유지한다.
2. **공개 상품 규칙 공급:** 권리자의 허용 범위와 갱신·철회 절차를 확보한 소량 자료부터 독립 실제 원문 검수·계산 golden test·기간·상품 매핑을 거쳐 기존 게시 흐름으로 넣는다. 이 문서의 링크 목록을 곧바로 운영 규칙으로 전환하지 않는다.
3. **개인 카드 자동 연결:** 직접 사업자 허가 또는 적법한 제휴 구조, 금융결제원/업권별 이용 자격·계약, 사용자 전송요구·철회, 상호 인증·키 보관·삭제·보안 시험을 정한 뒤 공식 테스트베드로 시작한다. 현행 “지갑·현재 위치 단말 처리” 원칙과 서버 처리 범위 변경의 영향을 다시 검토한다.
4. **실적·잔여·결제 코드 고도화:** 카드사가 제공하는 정확한 항목·업데이트 시각·개인 옵션·지원 상품 범위와 결제 체계의 공식 연동 권한이 확보된 부분만 연결한다. 공식 API가 없거나 계약이 미확정인 항목은 사용자 확인/공식 앱으로 남긴다.

필요한 외부 입력은 사업 주체·계약 담당자, 목표 카드사/상품 범위, 실제 데이터 이용권, 본인신용정보관리업의 해당성 검토·허가/제휴 구조, 운영 API 계약·보안 인증·예산이다. 개인 카드번호·CVC·금융 비밀번호를 개발자에게 보내거나 저장소에 입력할 필요는 없다.

조사 범위는 금융결제원 공개 개발자 목록·약관, 공식 마이데이터 카드 v2 규격, 금융위원회와 법령의 관련 안내, 신한 공식 API 공개 창구, 네 카드사의 대표 상품/앱카드 안내다. 비공개 제휴 상품·사업자 전용 상세 규격·모든 국내외 집계 사업자까지 전수 조사하지 않았다. 따라서 **“검토한 공개 공식 경로에서 무승인 범용 혜택·개인 실적·QR 집계 API를 확인하지 못했다”**가 이번 조사에 맞는 결론이다.
