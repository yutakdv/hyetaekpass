# 혜택패스 실현 가능성과 착수 기준

최종 기획 기준일은 2026년 9월 30일이다. **1~2인이 작은 생활권과 소량의 검수된 혜택으로 앱을 개발하는 것은 조건부로 가능하다.** 핵심 의존조건은 화면이나 AI 기능의 수가 아니라 데이터 이용권·개인별 조건의 불확실성·양 OS의 실제 위치 동작·정기 운영 시간이다.

이 문서는 현재 제품 범위의 사업·기술 판단과 검증·중단 조건을 정한다. 상세 설계는 [위치 정책](01_위치알림_정책과_검증.md), [데이터 운영](02_할인데이터_확보와_운영.md), [아키텍처](03_아키텍처_Docker_AWS.md), [실행 계획](04_개발계획_비용_출시운영.md), [법률과 개인정보](05_법률개인정보_및_출처.md)를 따른다.

## 1 확정 조건과 개발 전 확인

| 구분 | 현재 기준 |
|---|---|
| 개발 인원 | 1~2명. FE·BE·AI는 책임 구분이며 전담 인력 세 명을 뜻하지 않음 |
| 지원 플랫폼 | Android와 iOS 공통 개발. 플랫폼별 네이티브 기능과 공개 조건은 각각 검증 |
| 첫 실기기 | 보유 iPhone으로 먼저 검증. Android 실기기 확보는 공개 품질 검증의 의존조건 |
| 실행·배포 | BE·DB·선택형 AI는 Docker로 개발. 모바일 빌드는 플랫폼 도구 사용. 서버는 AWS, 앱은 각 스토어 배포 |
| 시간·예산 | 1인 주당 시간·경험·현금 예산 미정. 공수와 가용시간으로 일정 산정 |
| 초기 대상 | 한국 생활권 1곳, 브랜드 2~3개, 연구 후보 10~20규칙, 사용자 10~15명 |
| 데이터 상태 | 허가된 공개 카탈로그·자동 금융 연동·통합 피드는 아직 확보되지 않음 |
| 검증 상태 | 기기 성능·배터리·사용가치·실제 운영시간·법률 적용·AWS 실청구·스토어 승인 확인 필요 |

계획 범위를 최종화한 것과 개발·계약·심사를 완료한 것은 구별한다. 미정 항목은 실행 계획의 담당·결정 시점에 따라 해결한다.

## 2 범위별 진행 판단

| 범위 | 판단 | 진행 조건 |
|---|---|---|
| 로컬 보유 수단과 수동 혜택 확인 | 진행 | 지원 목록·출처·조건·삭제 제공, 표시 가능한 자료 확보 |
| 단순 정률·정액 예상 계산 | 진행 | 자격·산식·기준 금액·상한·반올림 검수, 미확인 조건 제외 |
| 전경 주변 목록 | 조건 충족 후 진행 | 점포 이용권·위치 관련 절차·양 OS 권한 UX와 실기기 확인 |
| 선택형 백그라운드 알림 | 초반 실험 후 판단 | 실행 기회·누락·오탐·결제 전 도달·배터리·심사·동의 통과 |
| 모호한 장소의 지역 안내 | 별도 선택형 실험 | 사용자 요청·묶음 조건·빈도·유용성 평가. 방문 확정으로 표현하지 않음 |
| 전국 카드·멤버십 자동 통합 | 초기 제외 | 재배포 가능한 피드와 지속 갱신·검수 인력이 생긴 뒤 검토 |
| 실적·잔여 한도 자동 조회 | 초기 제외 | 공식 금융 데이터 계약·사업 분류·보안 검토 필요 |
| 계정·동기화·영수증·포인트 최적화·B2B | 초기 제외 | 핵심 과업과 공급·운영 가치가 확인된 뒤 별도 범위 결정 |

2분 정지로 점포 입장·구매 의도를 확정하는 약속은 하지 않는다. Docker 성공·AWS 서버 운영·한 OS 검증도 각각 다른 OS와 스토어의 완료 증거로 대체하지 않는다.

## 3 고객 가설과 작은 검증

초기 사용자는 생활권 내 매장을 반복 이용하고 카드·멤버십을 두 종류 이상 보유한 사람으로 좁힌다. 최근 실제 결제 3건을 재구성하여 혜택을 몰랐는지, 조건이 어려웠는지, 결제 전에 기억하지 못했는지 구분한다. 마지막 문제가 주요 원인일 때 위치 알림의 가치를 우선 검증한다.

| 가설 | 검증 방법 | 시작 수용 기준 제안 |
|---|---|---|
| 안내가 결제에 도움 | 실제 보유 수단과 이용 매장으로 과업 수행 | 10명 중 7명 이상이 3분 안에 유용한 혜택 또는 확인 항목 발견 |
| 지원 데이터가 생활과 겹침 | 최근 방문·보유 수단과 지원 목록 대조 | 지원·자료 미지원·조건 미확인을 각각 보고. 규칙 개수로 커버리지 대체 금지 |
| 직접 입력을 감수 | 공식 조건을 읽고 보유 수단·모름·금액 입력, 중단 이유 기록 | 입력 포기가 많으면 화면과 범위를 바꾸고 다시 시험 |
| 알림이 기억을 도움 | 알림 없는 기간과 있는 기간의 실제 과업 비교 | 결제 전 도달·무관한 안내·끄기·놓친 방문을 함께 보고 |
| 데이터 유지가 가능 | 규칙 10건 작성·검수와 2주 갱신·제보 시간 측정 | 팀 가용시간에 맞는 운영량으로 제한 |

수치는 파일럿 가설이며 시장 수요·전체 유지율·통계적 효과를 증명한 값이 아니다. 같은 사람·경로·기기를 반복하면 결과가 편향될 수 있으므로 실패 사례와 표본을 함께 기록한다.

사용자 입력만으로도 시제품은 가능하다. 다만 데이터 허가 없이 입력형 계산기를 공개했다는 사실은 자동 혜택 발견 사업의 성공 조건이 아니다. 허가 데이터와 입력 마찰을 함께 해결하지 못하면 작은 파트너의 한정 혜택으로 공급·가치를 다시 검증한다.

## 4 정보 누락과 알림 품질

| 문제 | 최종 처리 | 평가에서 빠뜨리지 않을 것 |
|---|---|---|
| 횡단보도·정류장·정체와 방문 구별 어려움 | 기본 자동 발화를 제한하되 점포·혜택은 검색과 전경 목록에 유지 | 해당 장소의 실제 방문도 자동 알림 누락 분모에 포함 |
| 모호한 밀집 지역 | 사용자가 선택한 지역 묶음 안내 별도 실험 | 실제 지역 진입 전체, 사건 누락·보류·무관한 안내·피로 |
| 체류·OS 전달을 기다리다 결제 종료 | 결제 전 도달을 별도 평가 | 결제 뒤 도착한 알림을 성공으로 합산하지 않음 |
| 엄격 관측을 얻을 실행 기회가 없음 | 보류·만료하고 수동·전경 경로 제공 | 관측 가능한 방문만 분모로 고르지 않음 |
| 최신 혜택이 없음·자료 만료 | 계산·자동 안내 보류와 이유 표시 | 데이터 미지원과 위치 누락 구분 |

검색 목록을 유지해도 앱을 열지 않으면 놓칠 수 있다. 따라서 데이터 삭제를 막는 조치와 자동 발견의 누락을 줄이는 조치를 동일한 해결책으로 취급하지 않는다. 전체 혜택 발견, 기본 자동 안내, 선택형 지역 안내의 지표를 분리한다.

## 5 기술과 운영의 최소 기준

FE는 React Native·TypeScript 공통 앱과 하나의 단말 계산 엔진을 사용한다. BE는 소량 카탈로그·검수·릴리스·차단·제보·감사를 단일 서버에서 처리한다. AI는 허가된 비개인 자료의 후보 작성·변경 비교를 돕는 선택형 배치다. 사람이 더 빠르면 수동 경로를 유지한다.

지갑·현재 위치는 단말에 두고 서버에 이동 이력을 만들지 않는다. 실제 제보·IP·오류 SDK·운영자 정보는 개인정보 관리 대상으로 확인한다. 자료의 앱 표시와 단말 원시 규칙 배포 권리도 구별한다.

1인 팀은 실제 외부 검수자 없이 고위험 사전 탑재 계산 규칙을 공개하지 않는 품질 정책을 적용한다. 2인은 작성자 외 사람이 원문과 계산 사례를 확인한다. 역할 명칭이나 AI 검사를 독립 검수 증거로 삼지 않는다.

작은 카탈로그도 주당 약 5.5시간의 유지 업무가 들 수 있다는 계획 예시를 사용한다. 주당 시간 미정이므로 실제 시간 기록 후 규칙 수와 갱신 주기를 조정한다. 개발 중 운영·지원이 팀 가용시간의 20%를 2주 연속 넘으면 신규 소스 추가를 동결한다. 일정의 여유를 늘리거나 카탈로그를 줄이며, 확인일만 갱신하지 않는다.

## 7 착수와 공개의 결정 기준

착수는 실제 가용시간·기기·사업 주체를 기록하고, 데이터 10건과 양 OS 작은 빌드·iPhone 위치 관측으로 핵심 의존조건을 확인하는 단계부터 진행한다. 시뮬레이션과 개인 개발 시험을 공용 위치 서비스의 법률·동의 확인으로 대체하지 않는다.

공개는 필수 계산 사례 전부 통과, 자료 이용·검수·갱신·철회 근거, 양 OS 실기기, 기능별 위치·알림 품질, AWS 복구·제보·차단, 법률 적용과 각 스토어 승인을 증거로 판정한다. 아직 확보하지 못한 증거는 확인 필요로 남긴다.

입력형·전경 제품에도 사용가치가 없거나 자료 공급·유지 시간이 감당되지 않으면 출시 날짜를 맞추는 대신 제품 범위를 재결정한다. 공개 자동 알림은 OS·장소별로 증거가 있는 범위만 켠다.
