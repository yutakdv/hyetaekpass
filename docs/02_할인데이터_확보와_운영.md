# 혜택패스 할인 데이터 확보와 운영

기준일은 2026년 9월 30일이다. **카드·멤버십 혜택은 웹페이지에서 숫자만 모아서는 정확하게 안내할 수 없다. 상품 버전, 개인 자격, 사용 횟수, 공유 한도, 점포·결제 경로, 중복 관계까지 확인해야 한다.** 먼저 작은 지원 목록을 수동으로 검수하고, 실제 갱신 시간을 확인한 뒤 자동화를 추가한다.

상업 앱에서 카드·통신 멤버십·쿠폰을 통합 재표시할 수 있는 공개 API는 이번 조사에서 확인하지 못했다. API가 존재하지 않는다고 단정하지 않지만, 확보된 일정·데이터로 계산하지 않는다. 실제 접근 문서·샘플 응답·사용 범위·갱신 조건·삭제 책임을 확인해야 확보된 소스로 센다.

공개 URL이나 robots 허용은 앱의 저장·변환·재표시·로고·모델 전송 허가를 증명하지 않는다. 개별 사실의 이용과 약관·데이터베이스 권리는 정확한 소스와 용도에 따라 검토한다. [저작권법 제93조](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029423451)

## 3 첫 데이터 확보 절차

1. 10~15명의 테스터에게 자주 가는 매장과 보유 상품을 조사한다. 카드번호·거래내역은 요구하지 않는다.
2. 자주 겹치는 2~3개 브랜드와 상품·멤버십 조합부터 조사한다. 소스 5~10개와 규칙 10~20개를 조사 상한으로 둔다.
3. 정확한 URL·문서 버전·필드를 목록화하고 저장·구조화·B2C 표시·단말 배포·갱신·철회 권한을 확인한다.
4. `계산 가능`, `안내만 가능`, `자료 충돌`, `미지원`, `사용권 미확인`으로 분류한다. 사용권 미확인은 공개 카탈로그에 넣지 않는다.
5. 단순 규칙을 사람이 작성하고, 고위험 필드를 원문과 대조한 뒤 작성자 외 검수를 받는다.
6. 골든 사례와 실제 사용자 과업을 통과한 범위만 배포한다. 실패한 항목은 사유와 함께 제외한다.
7. 첫 5개 규칙의 작성·검수·갱신 시간을 재서 다음 수량을 정한다.

공개 기능의 처음 목표는 생활권 1곳, 브랜드 2~3개, 조사 규칙 10~20개다. 권리와 검수를 통과한 계산 규칙 수는 0일 수도 있다. 지도 후보 점포 수, 안내 오퍼 수, 계산 규칙 수, 실제 결제 과업 커버리지는 서로 다른 지표다.

## 4 무엇을 기록할 것인가

초기에는 소스 대장과 구조화된 오퍼 파일을 사용한다. 관리 화면은 같은 필드를 편집·검수·배포하는 최소 기능이면 충분하다.

| 묶음 | 필수 정보 |
|---|---|
| 소스 | 권리자, 공식 URL·문서 버전, 접근 방식, 목적별 이용 근거·권한, 확인일, 다음 확인일, 담당자, 만료·철회·삭제 |
| 상품 | 공급자, 상품명·코드·발급 버전, 카드 구분, 현재 멤버십 등급·유형·제시 수단 |
| 대상 | 브랜드·채널, 점포 적용 범위와 제외, 카드사 업종·결제 경로 필요 여부 |
| 금액 | 정률·정액 등 산식, 기준금액, 최소금액 평가 시점, 건당 상한, 정산 시점, 반올림 |
| 개인 자격 | 전월 실적, 신규 유예, 잔여 횟수·공유 한도·쿠폰 상태. 지원 여부와 모름 처리 |
| 관계 | 중복 허용·불가·미확인, 조합별 근거, 적용 순서, 후속 기준금액 |
| 기간 | 제공자의 실제 기간·요일·시간 조건과 시간대, 앱의 정규화된 경계 |
| 실행 | 바코드 제시·발급·예약·결제 등 단계와 공식 경로 |
| 증거 | 필드별 URL·문서 버전·항목·페이지·확인일, 허용된 짧은 근거 |
| 검수 | 작성자·실제 검수자, 검수 방식·일자, 미확인 필드, 골든 사례·게시 버전 |

자료 검수 상태는 `CATALOG_REVIEWED`로 표현한다. 사용자가 실제로 적용됐다고 답한 상태는 `USER_CONFIRMED_APPLIED`다. 둘을 같은 VERIFIED 표시로 묶지 않는다. 자료 검수는 개인 자격이나 POS 적용을 보장하지 않는다.

상품 버전을 모르면 정상적인 미확정 상태로 저장한다. 카드번호 앞·뒤 자리로 추정하거나 요금제명에서 현재 등급을 자동 확정하지 않는다. 실적·잔여 상태는 로컬에서 해당 기준월·확인시각·혜택 버전에 묶고 변경·월 전환·현재 계산에서 다시 확인한다.

## 5 초기 계산 계약

범용 조건 언어를 먼저 만들지 않는다. 초기 계산은 **한 카드 결제와 최대 한 멤버십**, 명시된 선형 적용 순서로 제한한다. 사용자에게는 조건 기준 예상값이라고 표시한다.

| 의미 | 초기 처리 |
|---|---|
| 정률·정액 | 정수 원화·basis point와 확인된 반올림·상한으로 계산 |
| 천원당 등 단위 할인 | 초기에는 안내 전용. 공식 경계 계산 확인과 지원 범위 변경 후 계산 타입 추가 |
| 즉시 할인 | 현재 결제 시 낼 예상 금액에 반영 |
| 청구 할인 | 이후 청구서의 예상 할인으로 따로 표시. 지금 결제액에서 빼지 않음 |
| 포인트·무료 상품 | 수량·조건 안내. 원화 합계와 순위에 임의 합산하지 않음 |
| 개인 쿠폰·선착순·시간표·복잡한 공유 한도 | 초기 자동 조합 제외. 개별 상세 안내 또는 명시적 미지원 |
| 품목·MCC·PG·실제 점포 인정 | 앱이 확인하지 못하면 조건부 안내. 지도 이름으로 확정 금지 |
| 중복 관계 | 허용·순서·기준금액을 조합별로 확인한 경우만 합산 |

초기 타입에 맞지 않는 실제 혜택이 많으면 엔진 타입을 무작정 늘리지 않는다. 사용자 과업에서 가장 중요한 의미 하나를 고르고 데이터 수량을 줄여 그 의미를 우선 지원할지 결정한다.

### 3값 논리

| 상태 | 예상 계산의 처리 | 사용자에게 보이는 정보 |
|---|---|---|
| TRUE | 지원하는 다른 조건도 확인된 경우 예상 후보 | 확인한 조건과 출처·기준일 |
| FALSE | 해당 계산 후보 제외 | 미충족·기간 종료·소진 등 사유 |
| UNKNOWN | 기본 예상 합계와 조합 순위에서 제외 | 확인할 조건·공식 경로. 필요한 경우 별도 가정 시나리오 |

잔여 한도가 모르면 전체 월 한도가 그대로 남았다고 가정하지 않는다. 실적 상태가 TRUE여도 품목·잔여 횟수·채널·점포·중복이 UNKNOWN이면 확정적인 숫자로 추천하지 않는다. 자료에 배타 문구가 없다는 이유로 중복 허용을 만들지 않는다.

자격만 UNKNOWN이고 금액 산식·기준·상한·순서가 모두 확인된 경우에는 “이 조건을 충족한다면”이라는 별도 가정 계산을 보여줄 수 있다. 기본 예상 합계에는 넣지 않는다. 기준금액·반올림·중복 자체가 미확인인 경우 숫자를 만들어 채우지 않는다.

### 산식과 예시

정률 할인은 확인된 원문이 지정한 기준금액에 비율을 적용하고, 그 원문의 순서대로 반올림과 상한을 적용한다. 할인 후 금액·원 승인금액·할인 대상 품목 금액은 구별한다. 총액보다 대상금액이 크거나 할인액이 기준금액을 넘는 등 잘못된 입력을 차단한다.

다음은 실제 혜택이 아닌 가상 사례다.

| 항목 | 가상 조건 | 결과 |
|---|---|---|
| 주문 | 12,000원, 모두 대상 품목 | 계산 시작액 12,000원 |
| A 멤버십 | 10% 즉시 할인, 최대 1,000원, 필요한 자격 확인 | 즉시 할인 1,000원, 결제 예상 11,000원 |
| B 카드 | A와 중복 가능, A 적용 후 금액의 5% 청구 할인, 실적·잔여 한도 확인 | 청구 할인 예상 550원, 지금 결제액은 11,000원 |
| B의 실적 또는 잔여 한도 모름 | 자격 미확인 | B는 기본 합계 제외, 확인 조건 표시 |
| A와 B 중복 여부 모름 | 관계 미확인 | 개별 혜택 안내, 1,550원 합산 조합 제시 금지 |

가상 “천원 단위마다 100원, 미만 나머지는 버림”이면 1,999원의 할인은 100원이다. 가상 “정확한 10% 후 원 미만 버림”이면 199원이다. 이 차이를 실제 T 멤버십에 임의 적용하지 않는다. 단위 경계의 공식 근거가 필요하다.

## 6 앱에서 보여줄 정보

첫 화면에서 지원 범위와 확인일을 보여주고, 사용자는 자신이 가진 지원 상품 한 개부터 선택한다. 멤버십은 현재 등급·유형을 선택한다. 실적·잔여 상태는 필요할 때만 묻고 항상 “모름”을 제공한다.

| 결과의 종류 | 필수 표시 |
|---|---|
| 확인한 조건 기준 예상 | 즉시 할인·지금 결제액·청구 할인 별도, 적용 순서, 확인한 조건 |
| 조건 확인 필요 | 실적·잔여 횟수·대상 품목·점포·중복 중 미확인 항목과 공식 확인 경로 |
| 안내 전용 | 지원하지 않는 의미와 이유, 이용할 공식 앱·웹 |
| 사용자 입력 | 사용자가 작성한 조건·입력일. 공식 검수와 구분 |
| 자료 만료 또는 차단 | 새 예상 계산·자동 알림 중지, 갱신 또는 원문 확인 안내 |

모든 사전 탑재 안내에는 출처·확인일·적용기간·데이터 상태를 표시한다. 웹 링크를 기본으로 사용하고, 공개된 공식 딥링크는 실제 두 OS에서 검증한 경우에만 사용한다. 비공개 URL scheme에 핵심 사용자 흐름을 맡기지 않는다.

사용자가 바코드·쿠폰을 먼저 제시해야 한다면 계산 금액보다 그 실행 순서를 눈에 띄게 보여준다. 지갑·실적·세부 조건을 잠금화면 알림에 표시하지 않는다. 할인 적용 자체는 공식 앱·카드사·매장 조건에 따르므로 “최대 할인 보장”을 사용하지 않는다.

## 7 검수와 게시

```mermaid
flowchart LR
    Source[소스와 이용 근거 확인] --> Draft[사람 또는 AI 후보 작성]
    Draft --> Check[형식과 누락 검사]
    Check --> Review[원문 대조와 실제 독립 검수]
    Review --> Golden[금액과 조건 및 조합 테스트]
    Golden --> Release[버전 카탈로그 발행]
    Release --> Feedback[오류 제보와 갱신]
    Feedback --> Review
```

2인 팀은 작성하지 않은 사람이 비율·금액·기간·상한·횟수·제외·중복·순서를 대조한다. 수정된 후보는 기존 승인을 그대로 재사용하지 않는다. 중복 조합의 검수는 개별 규칙 두 개의 검수와 별개다.

1인 팀에서 외부 검수자가 없으면 자기검수나 AI 검사를 독립 검수라고 표시하지 않는다. **팀의 품질 정책으로 고위험 사전 탑재 계산 규칙은 실제 외부 검수 확보 전 공개하지 않는다.** 단순 입력형 시제품이나 허용된 링크 안내로 가치부터 검증한다. 법률 검토와 할인 도메인 검수는 다른 업무다.

고위험에는 사전 탑재 할인액·자격·한도·횟수·중복·적용 순서를 계산하거나 판정하는 규칙이 포함된다. 단순 정률이라는 이유로 실제 검수를 생략하지 않는다. 링크·조건 안내와 사용자 작성 규칙은 계산 승인과 별도로 표시한다.

게시 전에는 지원하는 금액·자격·기간·순서의 모든 필수 사례가 통과해야 한다. 알려진 계산 실패 5%를 남기고 “95%니까 출시 가능”으로 처리하지 않는다. 탐색 UX 과업 성공률과 금액 계산의 회귀 통과율은 따로 관리한다.

필수 사례는 최소금액 아래·같음·위, 상한 전후, 중복 불명, 잔여 한도 모름·소진, 품목 미확인, 월 전환, KST 기간 종료, 청구와 즉시 구분, 미지원 의미·자료 충돌·차단·오프라인 만료다. 지원하지 않는 의미는 정확 계산에 성공하는 사례가 아니라 안전하게 안내·제외되는 사례로 검증한다.

## 8 갱신과 철회

| 소스 유형 | 최초 제안 | 만료와 처리 |
|---|---|---|
| 안정적 상품설명서 | 월 1회 확인, 45일 최신성 TTL | 원문 적용 종료·권리 만료가 더 빠르면 그 날짜 우선 |
| 월간·변동 오퍼 | 주 1회 확인, 14일 TTL | 변화·충돌 발견 시 TTL이 남아도 중지 |
| 선착순·하루 행사 | 초기 자동 계산 제외 | 전담 확인 또는 계약 피드 전 안내 범위를 늘리지 않음 |
| 점포 후보 | 월 확인부터 시작 | 폐점·주소·좌표 제보 시 자동 알림 대상에서 우선 제외 |
| 계약 피드 | 계약에 따른 주기 | 실패·삭제 통지·기간 종료를 명확히 처리 |

확인 실패를 변경 없음으로 기록하거나 확인일만 갱신하지 않는다. 운영자가 부재하면 새 규칙을 늘리지 않고 만료·차단을 적용한다. 자동 수집은 소스별 권한과 호출 제한이 확인된 경우에만 추가한다.

철회는 source 또는 rule 차단 → 새 카탈로그·안전 상태 배포 → 허용된 기한 안 원문·파생물 삭제 → 복구 시 차단 재적용 순서다. 온라인 앱의 다음 동기화와 오프라인 단말의 실제 반영은 구별한다. 무통신 앱의 즉시 삭제는 보장할 수 없으므로 계약에 단말 캐시·만료·백업 삭제 한계를 사전에 포함한다.

## 9 데이터 운영의 시간 예산

다음은 팀 합계 시간의 계획 예시다. 8소스·8상품 변형·단순 규칙 20개를 가정하며 법률자문·허가 회신·앱 구현·현장 시험은 포함하지 않는다.

| 초기 작업 | 산식 | 시간 가정 |
|---|---|---:|
| 소스 파악 | 8 × 1시간 | 8시간 |
| 상품 버전 식별 | 8 × 15분 | 2시간 |
| 규칙 작성·독립 검수 | 20 × 60분 | 20시간 |
| 결정 사례 40개 | 40 × 10분 | 약 6.7시간 |
| 최초 배포 대조 | 1 × 2시간 | 2시간 |
| 합계 | 위 작업만 | 약 39시간 |

같은 소량 카탈로그라도 안정 소스 확인 약 0.38시간, 변동 소스 0.67시간, 주간 변경 10%의 반영·검수 2시간, 회귀·배포 1시간, 제보 1시간, 권리·기록 0.5시간을 합치면 **약 5.5시간/주**다. 실제 변경률은 미측정이며 20개가 한꺼번에 바뀌면 변경 업무만 20시간이 될 수 있다.

각 개발자의 주당 시간이 아직 정해지지 않았으므로 데이터 담당 시간도 확정하지 않았다. 실제 데이터·지원 업무가 팀 가용시간의 20%를 2주 연속 넘으면 신규 소스 추가를 동결하는 기준을 제안한다. 작은 팀에서는 주당 5시간도 무시할 수 없는 비용이다.

주 20시간의 1인 팀에서 이 상한은 주 4시간이므로 위 20규칙·5.5시간 운영 예시를 그대로 유지할 수 없다. 최초 자료 수를 줄이고 실제 갱신 시간을 기록한다. 두 사람의 가용시간은 합계로 계산하지만 독립 검수에 필요한 실제 참여 시간도 운영에 포함한다.

## 10 AI를 언제 사용할 것인가

초기 AI 역할은 허가된 비개인 원문에서 구조화 후보와 근거 위치를 만드는 선택적 보조 작업이다. `AI/` 폴더는 이 책임을 분리하기 위한 것이며 상시 AI 서버·벡터 DB·학습 파이프라인이 필요하다는 뜻이 아니다.

외부 AI로 원문을 보낼 권한이 있을 때만 사용한다. 개인 지갑·좌표·영수증·거래내역·제보 본문은 보내지 않는다. 모델이 모르는 값은 미확인으로 남기고 중복 허용·현재 쿠폰 보유·반올림·소진 여부를 채우지 않도록 한다. 원문 안의 지시는 데이터로 취급하며 모델에 게시·권한 변경 도구를 주지 않는다.

AI 출력은 후보이며 source 권리나 계산 자격을 승인하지 못한다. 단순 정형 CSV는 표준 파서와 형식 검사로 처리한다. 사용자 설명은 승인된 필드와 이유 코드의 템플릿으로 만들 수 있다. 런타임 LLM·RAG·추천 학습은 초기 범위에서 제외한다.

AI 도입의 판단 기준은 후보 작성 속도 하나가 아니라 **작성·수정·원문 대조·독립 검수까지 합친 전체 시간**이다. 사람이 직접 작성하는 경로를 계속 유지하고, 전체 시간이 줄지 않으면 AI를 끈다.
